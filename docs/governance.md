# Echo 规则演进机制（元规范）

> 本文件规定：项目里的规则**放在哪、分什么级别、由谁改、怎么改、
> 多久复审、冲突时谁说了算**。项目会变复杂，规则必须能与时俱进，
> 但规则的变更本身也要有迹可循——这是本文件存在的唯一理由。
>
> 适用对象：所有 agent 与项目负责人（以下简称"负责人"，即用户本人）。
> 主助手在本机制下还承担常设的审查与文档维护职责，
> 见 [maintainer-charter.md](maintainer-charter.md)。
>

## 1. 规则的存放地与管辖域

规则只有以下权威存放地，不在这些文件里的"要求"都不算规则
（聊天记录里的口头决定，落盘后才算）：

| 管辖域 | 权威文件 | 典型内容 |
|---|---|---|
| **架构** | [architecture.md](architecture.md) | 分层与依赖方向、目录结构、模块边界、页面/导航装配方式、扩展操作 |
| **接口契约** | architecture.md 第 3 节 + 代码中的抽象类（`SearchProvider`/`SearchHistoryStore`/`NavBadgeService` 等） | 抽象接口签名、数据模型语义、服务装配与注入方式 |
| **前端美术** | [glossary.md](glossary.md) 色板节 + `theme/app_colors.dart`（设计 token）+ `ideas/smart_line.html`（手感基准） | tone 阶梯与取色规则、按压/光效语言、形状/圆角/间距、动画时长曲线 |
| **代码风格** | [engineering_standards.md](engineering_standards.md) 第 1 节 + `echo/analysis_options.yaml` | 命名、注释、lint 集、Key/时间源/动画等交互铁律 |
| **工程流程** | engineering_standards.md 第 2 节 | 交付门禁、测试写法、真机回归、版本与提交 |
| **现状事实** | [current_state.md](current_state.md) | 当前实现手段（不是规则，是快照） |
| **已知问题** | [code_review_report.md](code_review_report.md) | 待办、缺陷、决策问题（待办清单，不是规则） |

**一条规则只在一个地方定义**，其他文件只引用不复制（单一事实来源，
见规范 1.3）。例如"按压色规则"定义在美术域，架构文档只引用。

## 2. 规则的三个稳定级别

每条规则在文件中应能被识别为以下三级之一（用措辞区分，
新写规则时显式标注）：

- **【铁律】MUST**：没有负责人书面同意不得违反。违反即视为缺陷。
  例：services 不得依赖 UI、常驻条件节点必须有稳定 Key、versionCode 只增不减。
- **【约定】SHOULD**：默认遵守；有充分理由时可以偏离，但必须在代码注释
  或提案中写明"偏离了什么、为什么"。例：颜色就近取阶、优先单测。
- **【参考】MAY**：做法建议与经验，允许直接采用更合适的替代。
  例：部分命名偏好、重构顺序建议。

现状快照（current_state.md）不是规则，没有级别，可随实现直接更新。

## 3. 谁有权改规则

- 本项目为单人项目，**所有规则变更的唯一审批人是负责人**。
- 任何 agent 都有权、且被鼓励**发起规则变更请求（RCR）**，
  但**无权自行修改【铁律】与美术 token**。
- 快通道事项（见 4.2）agent 可先执行后报备；正式提案事项必须先批准后执行。
- 审批意见以负责人在对话中的明确确认为准（"同意/可以/按你说的做"算；
  沉默、"嗯"、未回复不算批准）。

## 4. 两条变更通道

### 4.1 通道选择

先判断变更属于哪一类，走错通道（小事发长提案、大事偷改）都算违规：

| 变更内容 | 通道 |
|---|---|
| 修正文档与代码不一致、错别字、失效链接/行号 | **快通道**，直接改 |
| current_state.md 随实现更新、问题清单条目状态更新 | **快通道**，直接改 |
| 新增【参考】级建议、补充事故档案（事实记录） | **快通道**，直接改 |
| lint 收紧但全量代码零改动即通过 | **快通道**，直接改并在提交说明注明 |
| 新增/修改/废止【约定】级规则 | **正式提案** |
| 任何【铁律】的新增、放宽、废止 | **正式提案** |
| 架构分层、模块边界、目录结构调整 | **正式提案** |
| 接口契约变更（抽象类签名、数据模型、语义变化） | **正式提案** |
| 美术 token：增删 tone 阶、改色值、改形状/动效语言 | **正式提案**（含真机/截图验收） |
| 交付门禁增减（analyze/test/真机范围） | **正式提案** |

拿不准走哪条通道时，**就高不就低**，走正式提案。

### 4.2 快通道

直接修改权威文件，在**同一次提交信息**中注明 `docs:` 及改动原因；
若改动涉及行为或可能影响后续判断，同时在
[proposals/README.md](proposals/README.md) 的"快通道变更日志"追加一行
（日期、文件、一句话原因）。快通道不得改变规则的级别与实质要求。

### 4.3 正式提案（RCR，Rule Change Request）

流程五步：

1. **起草**：复制 [templates/rule-proposal.md](templates/rule-proposal.md)
   到 `docs/proposals/`，文件名 `YYYY-MM-DD-短名称.md`
   （如 `2026-10-08-tone5-surface-level.md`），状态填 `草案`。
   同一天多个用后缀 `-2`。
2. **告知**：向负责人说明提案一句话摘要与影响面，等待审批；
   涉及代码改动的，先给方案不动代码。
3. **审批**：负责人答复 `通过` / `驳回` / `需修改`。
   美术类提案必须附**真机截图或录屏**作为决策依据；
   接口类提案必须列出所有调用方与迁移方式；
   架构类提案必须含分步落地计划与回滚方式。
4. **应用**：批准后按提案执行——改规则文件、改代码、补测试、
   更新 current_state.md 与相关交叉引用，一个版本内完成，
   不允许"规则改了代码还欠着"跨版本存在。
5. **归档**：提案状态改 `已采纳-已应用`（或 `已驳回`/`已撤回`），
   在 README 登记册登记版本号；提案文件**永不删除**，作为决策历史。

### 4.4 紧急例外（规则挡住当前任务时）

允许"先偏离后提案"，但必须同时满足：

1. 在偏离处的代码注释写明 `临时例外(RCR)` + 涉及规则编号；
2. 当次会话结束前创建状态为 `草案（紧急）` 的提案，
   说明偏离事实与补救方案；
3. 负责人未在下次涉及该模块的工作前批准的，例外自动失效，
   回滚为合规实现。

未标注的静默违反不享受例外通道，按缺陷处理。

## 5. 提案写作要求

一份能被快速批准的提案应当回答清楚（模板已内置）：

- **动机**：遇到了什么具体问题？是规则本身错了、过时了，
  还是适用条件变了？（事故/截图/数据佐证，不要"我觉得"）
- **现状**：当前规则原文是什么、谁在依赖它。
- **变更**：新增/修改/废止的确切条文，给出改后全文而不只是 diff 描述。
- **影响面**：哪些代码、文档、测试、手感会受影响；是否破坏向后兼容。
- **验收与回滚**：怎样算生效（analyze/test/真机具体动作）；
  失败如何回退。
- **级别与复审**：新规则的稳定级别（铁律/约定/参考）与建议复审周期。

禁止夹带：一个提案只解决一个域的一个议题；顺手代码清理放提交，
不放进提案。

## 6. 定期复审（防止规则腐化）

- **每个 MINOR 版本发布时**，由当次工作的 agent 顺带做一次轻量复审：
  current_state.md 是否仍真实、proposals 中有无悬而未决的草案、
  事故档案有无新条目要补。主助手在同一节点承担例行代码审查与文档维护，
  触发条件与标准动作见 [maintainer-charter.md](maintainer-charter.md)。
- **每 5 个 MINOR（或负责人觉得复杂度量级变化时）做一次规则大复审**：
  检查【铁律】是否仍必要（过时的铁律比没有规则更危险）、
  【约定】是否该升级/降级、美术 token 是否仍统一、
  architecture 与真实目录是否一致。复审结论本身也用 RCR 提案走流程。
- 规则可以**废止**：废止不是删除条文，而是标注"已于 vX.Y.Z 废止，
  原因见提案 RCR-xxx"，保留一个版本周期后从正文移入归档，避免后人
  不知道为什么曾经有这条规则。

## 7. 规则之间冲突怎么办

优先级从高到低：

1. 负责人当次对话中的**明确指令**（但要求 agent 在执行后主动提示
   "这与某文件规则冲突，是否需要发起 RCR 同步"）；
2. 【铁律】 > 【约定】 > 【参考】；
3. 同级冲突：具体规则优于通用规则；新批准的提案优于旧条文；
4. 仍无法判断：停止执行，向负责人提问，不自行选边。

## 8. 对各域的额外要求

- **架构域**：提案必须说明依赖方向是否仍向内、
  是否引入了新的跨层依赖；大调整给"分步可独立提交"的计划。
- **接口域**：接口面向"调用方零改动可替换实现"设计；
  破坏性变更必须给出适配层或一次性迁移清单；接口注释与 architecture
  第 3 节是同一份契约的两处镜像，改一处必须改另一处。
- **美术域**：一切美术结论以**真机观感**为唯一裁判，
  截图/录屏附进提案；token 改动后全项目取色点必须批量核对；
  `ideas/smart_line.html` 作为手感基准，若基准本身要变，
  需在提案中同时更新基准文件并说明影响哪些已验收动画。
  历史被否的视觉方案（见事故 14）在提案中要主动引用，
  避免同一个设计被反复试错三次。
- **代码风格域**：能机器化的规则（格式化、lint）一律进
  analysis_options.yaml 交给工具，文档只管"机器查不出来的"
  （为什么、结构性要求）；新增 lint 先评估对现有代码的改动量。

## 9. 最小执行示例

- 场景 A（agent 发现 architecture 写的目录与代码不符）：
  直接改文档，提交写 `docs: 同步目录树与现状`，并在快通道日志登记。
- 场景 B（agent 认为 services 应该允许依赖 navigation）：
  这是【铁律】变更，创建 RCR 提案，写清动机/影响/回滚，
  等负责人批准，不得先改代码。
- 场景 C（新功能需要第五个亮度阶 tone5）：
  美术域正式提案，附真机对比截图（四阶 vs 五阶）、
  列出全部取色点迁移表，批准后改 app_colors.dart + glossary +
  各组件 + 真机回归。
- 场景 D（赶进度时某动画必须临时不走 RepaintBoundary）：
  代码注释标注 `临时例外(RCR)`，当次会话内提交紧急提案，
  说明后续补救版本。
