## 1. 原则

### 1.1 版本、分支与提交纪律

**版本号**（见 `echo/pubspec.yaml`）：

- `0.MINOR.PATCH+BUILD`：MINOR 在功能更新时 +1；PATCH 在 bug 修复时 +1，
  MINOR 增加时 PATCH 清零；首位 0 保持到正式发布，正式发布时升 1.0.0；
- `+N`（Android versionCode）**永远只增不减**，即使版本名回退；
- 每个版本节点打 git tag（如 `v0.5.0`，本地轻量 tag）。
- **版本号由主线分配，不在任务分支上预占**（避免多 agent 并行时各自从分叉点
  数出同一个号）：
  - 任务分支开发期间 pubspec 版本号**保持分叉时的旧值不动**；需要装机验证
    时直接构建即可（adb 允许同号覆盖安装），不要先给自己"预留"一个新版本号。
  - 合并者负责排号：合入 main 前看 main 当前版本与已有 tag
    （`grep '^version:' echo/pubspec.yaml && git tag`），按改动类型取下一号，
    在合并提交或紧随的 release 提交中改 pubspec 并打 tag。
  - 若分支上已经预占过号、与 main 撞车：main 已占用的号归属不变，
    后合入者顺延（案例：2026-10-07 两个分支都占了 v0.5.3+26，
    快捷弧分支合入后顺延 v0.5.4+27）。
  - 例外：单个 agent 在 main 流上快速闭环（建分支→修→立刻合回，无其他并行
    任务）时，可在修复提交中直接升 PATCH，不必等合并时再改。

**远程仓库与 tag 推送**（origin = `https://github.com/HaitoPhenol/Echo.git`）：

- `git push`（任何形式，含首次推送）仍须用户明确授权后执行。
- 远程只保留功能里程碑：**只推 MINOR tag（`vX.Y.0`），patch tag 留本地**。
  用 `git push origin $(git tag -l 'v*.*.0')` 逐个推，
  **禁止 `git push --tags` / `--follow-tags` 一把梭**（会把 patch tag 全推上去）。
- 分支全部同步到远程（含已合并的功能分支；远程分支同样不删除）。
- 一旦推送，tag 与公共提交视为**不可变**：不改指、不删远程 tag、不 force push。

**提交信息**：用 Conventional Commits —— `feat:` 新功能 · `fix:` 修复 ·
`refactor:` 重构 · `docs:` 文档 · `chore:` 杂项；标题简述，正文说明原因。
不 amend、不 force push。

**分支纪律**：

- main 只接收合并，**不在 main 上直接做功能开发**。
- 接到新任务时先看 `git branch --show-current`：若在 main 或别的任务分支上，
  **主动向用户提议创建本任务分支**（`feat/xxx` / `fix/xxx`），确认后开工；
  用户已明确授权时可直接创建。**建分支前先同步最新 main**
  （从最新 main 切出；分叉后 main 前进了，合并前先 rebase 到最新 main，
  减少分叉与版本撞号）。
- **开工前与合并前各看一眼其他分支的状态**（`git branch -vv`、
  `git log --all --oneline -- echo/pubspec.yaml`）：知道有谁并行、
  谁可能占用版本号；但排号以合并时 main 的实际状态为准。
- **每次提交前再次确认当前分支是自己的任务分支**；不是就先停下切换，
  不得把代码提交进别人的分支或 main。带着未提交改动切换前必须确认不会污染
  目标分支，拿不准则问用户。
- 任务完成并验收后，可顺手把任务分支**快进合并**到 main；发现已分叉
  （不能 ff-only）则不自动合并，交用户决定。**任何情况下不删除分支**，
  除非用户明确要求。
- **每次把代码合并到 main 之后，立即构建并安装到手机**做一次冒烟验证
  （当前命令：`cd echo && flutter build apk --debug` →
  `adb install -r build/app/outputs/flutter-apk/app-debug.apk` → 启动主 Activity）；
  纯 docs 合并无代码变更可跳过但要说明，发版节点按用户要求改用 release 包。
  无设备连接 / adb 不可用时报告原因并跳过，不得假装已验证。
- 例外：主维护助手（审查/文档职责）的**纯文档改动不单独开分支**，
  跟随当前最新的工作分支以 `docs:` 提交即可。

**哪些事可以自主、哪些必须问**（2026-10-07 负责人授权）：

- 可自主，不必每次问：修完一个**可独立验证的最小修复单元**（小 bug / 小优化，
  含回归测试与门禁）后，PATCH +1、`+N` +1，`fix:`（或 `chore:`）提交并打
  本地 tag，完成后汇报。最小颗粒 = 不相关的 bug 不共用一个 patch，
  一个修复也不拆成多个 patch。**但版本号不预占**：并行任务分支上只提交代码，
  排号在合入 main 时按主线规则统一做（见上"版本号由主线分配"）。
- 必须先问用户：MINOR 功能版本（`0.x.0`）升号与发版、1.0.0、`git push`
  （含 `--tags`）、删除/重置分支等破坏性操作；改动拿不准算 MINOR 还是 PATCH
  时也问。
- 纯文档改动（`docs:`）不升版本号。

### 1.2 文档与代码保持一致

- 每次新增或改动功能后，做文档对照审计：[architecture.md](architecture.md)、
  [glossary.md](glossary.md) 与源码逐句核对（术语、文件位置、数值、数量），
  发现过时描述立即修正。
- 注释解释"为什么"和适用条件，而不只是"做什么"。手段变更时注释必须跟着改，
  不允许注释描述一个已经不存在的实现。

### 1.3 单一事实来源与配置驱动

- 每类信息只有一个权威来源。例如"有哪些页面"只由导航配置描述，
  界面、指示器、搜索都从同一份配置读取，禁止各处各写一份。
- 新增同类内容优先走"加一条配置"，而不是改框架代码。
- 同一数值（几何尺寸、时长、热区等）只允许定义一次，视觉与命中共用同一来源；
  发现重复常量要收敛，不得再复制粘贴一份。

### 1.4 依赖方向（分层意图）

- 依赖只能向内：`pages` → `navigation` → `services` → `theme`。
  **services 不得依赖 navigation/pages 等 UI 层**。
- 可复用能力（搜索、触感、状态服务）面向抽象接口定义，UI 依赖抽象而非具体实现；
  换实现（如内存存储换持久化）时调用方零改动是设计目标。
- 文件按职责归位，不要把文件放得到处都是；优先编辑已有文件，不新建文件除非确有必要。

### 1.5 视觉规范

- 颜色集中在调色板（`theme/app_colors.dart`）统一管理，按"语义"或"视觉亮度层级"
  取色，**禁止在组件里散落裸十六进制值和临时透明度**；新增视觉元素时先在调色板找
  对应语义，没有合适的就先补具名常量再使用。调色板的阶数与取值可随设计演进，
  但"集中管理"不变。
- 同一交互反馈在各组件中保持一致（按压色、动画时长语言等），不逐组件各做一套。
- 动画中的连续 alpha（脉冲、呼吸、急闪）允许跨阶插值，但基色必须用具名常量，
  不写裸 `Colors.white`。
- **机能风视觉层专用色**集中在调色板的 `mech*` 色组（15 个 token，
  RCR-2026-001 收编），与 tone1～tone4 亮度阶**并列、互不归并、互不混用**：
  导航/浮层体系取 tone 阶，背景纹理/读数条/大页码/转鼓取 mech 色组。
  机能风的几何、排印、时长常量同样只允许在
  `theme/mechanical_style.dart` 的 `MechanicalStyle` 定义一次
  （该文件不得再放颜色）。

### 1.6 元素身份必须稳定

- 在 Stack/Row/Column 中以 `if`/`for` 条件插入子节点时，需要跨帧保持身份的
  常驻节点必须带稳定 Key。框架按类型 + 位置配对元素：无 key 节点插入中部会使
  后续兄弟元素整体错位、渲染对象销毁重建，动画因此静默失效（事故 1）。
- 判断标准：这个节点是否需要跨帧保持同一个渲染对象 / State？需要，就给稳定身份。

### 1.7 差异形态之间要解耦，不做"万能变形组件"

- 当一个组件要在两种差异很大的形态间形变（如静止导航条 ↔ 全宽搜索框），
  用两个解耦组件在切换帧交接（起始外观一致使切换不可察觉）。
  合成一个组件必然出现覆盖层层级错乱、收回途中内容穿帮（事故 3）。

### 1.8 几何的事实来源唯一，且视觉与命中一致

- 可点击区域必须与用户看到的位置对齐，且二者从同一份几何数据推导。
- 运行时测量（GlobalKey 等）与静态推算都只是手段。无论用哪种，都要保证冷启动
  首帧稳定、不出现重挂载 / 断言问题。若改用运行时测量，必须先验证低端机冷启动
  并说明相对当前方案的收益（事故 4）。

### 1.9 时间相关行为要可确定地测试

- 物理模拟、倒计时等时间驱动逻辑，其时间源应能在测试中被确定性推进
  （当前实现选用帧时间戳而非墙钟，正是为此）。
- 在帧外（普通事件回调）不要直接读取可能过期的帧时间戳作为计时基准；
  需要基准时惰性记录于生效后的第一个帧（事故 5）。
- 墙钟 Timer 与帧时钟是两条时间线（App 后台、测试 pump 时行为不同）。
  同一状态机内混用必须想清每条线的语义；新增延时先判断它属于"动画 / 物理"
  还是"真实世界等待"，再选时间源。

### 1.10 动画性能原则

- 逐帧动画期间消除重布局：动画值只驱动变换 / 透明度 / 绘制，避免每帧改变约束。
  复杂内容固定尺寸放置、超出部分裁剪，需要隔离重绘时用 RepaintBoundary（事故 6）。
- 循环光效必须有逐帧重建的订阅（如 AnimatedBuilder），不能只在首帧取一次动画值，
  否则会"冻结"（事故 7）。
- 多个 AnimationController 并存于一个 State 时用 TickerProviderStateMixin。
- `didUpdateWidget` 中比较新旧状态时，不要读同一个可变对象的现值（新旧 widget
  拿到的都是现值，永远相等）；由父级 build 时把值捕获为不可变字段传入。
- 自适应内容不要用会改变自身尺寸行为的对齐方式（Container 加 alignment 在有限
  宽度下会撑满，事故 2）；需要按内容自适应并居中时用 `Center(widthFactor: 1)`。
- **描边与阴影画在裁剪层之外**：`Border` 的线跨盒缘（一半在盒外），
  放在 ClipRRect 内会被裁掉外侧半条、整圈变细；把"颜色+边框"合成的 DecoratedBox
  放在裁剪层外，ClipRRect 只裁内容，阴影同理（事故 11）。
- **动画中的圆角要显式夹取**：不要传 999 一类超大名义半径——渲染器横纵独立夹取
  （rx 夹宽/2、ry 夹高/2），形变过程中会产生椭圆角、端部像矩形遮罩。
  每帧按当前外框宽显式 `r.clamp(0, frameWidth / 2 - inset)`，保证两端始终半圆
  （事故 11）。
- **被前景遮挡的元素优先用物理遮挡，不要写位置显隐逻辑**：例如锚点始终全部挂载、
  画在不透明滑块下层，当前页段被物理盖住、拖动时自然滑入滑出。
  按位置阈值（如 <0.5）挂载/卸载会在临界点元素恰在前景边缘时突然弹出露馅
  （事故 13）。
- 验证动画是否真播放：读渲染对象身份（跨帧必须不变）与中间尺寸（应插值而非
  一步到位）；真机用 `dumpsys gfxinfo <包名>` 看 Janky frames / Missed Vsync。

### 1.11 行为必须有反馈

- 不允许出现"按了没反应"的控件：功能未实现时给明确占位反馈，
  触感、视觉、语义至少占其一。
- 非关键能力（如触感）失败时静默降级，不得打断交互主流程。

### 1.12 手感参数以真机验收为准

- 物理曲线、动画时长、热区等手感参数属于调参结论，改动前后必须真机对比
  （构建安装 → 实际手势操作 → 录屏 / 截图比对），模拟器与单元测试不能替代。
  具体取证命令见 1.15。
- 参数集中、具名、注明取值依据与适用条件（如"按 N 页场景压低"）。
  适用条件变化（页面数量、设备形态）时整体重新评估，不把调参注释当永久真理。
- 真机帧率以连续操作时 `dumpsys gfxinfo <包名>` 的 Janky / Missed Vsync
  帧数为准（部分 MIUI 版本 Total frames 显示 0 是系统怪癖，不代表没跑帧）；
  屏幕录制本身增加负载，录屏时测到的是最差工况。

### 1.13 最小依赖与工具变更

- 依赖与工具链服务于需求，不为"先进"而引入：新增三方依赖 / 框架前，
  先说明现有手段为什么不够、迁移成本与替代方案。
- 反过来，当现有手段确实成为阻碍时可以更换——工具不是规定，
  "按需、审慎、可回退"才是。更换后更新 [current_state.md](current_state.md)。

### 1.14 命名与文件

- 文件名 `snake_case.dart`，类名 `UpperCamelCase`。
- 非通用配置不放仓库根目录。
- 公共 API 写文档注释，重点说明"为什么"。

### 1.15 真机取证工具链（截图 / 录屏 / 抽帧合成）

以下为当前真机验收的具体操作手段（设备：小米 MIX 2S，1080×2160 物理像素、
density 440，即 1dp = 2.75px；包名 `com.everse.echo`）。工具可换，
换设备后坐标与换算系数要重新核对。

**公共路径**：

```bash
ADB=/home/phenol/Android/Sdk/platform-tools/adb
FLUTTER=/home/phenol/development/flutter/bin/flutter
```

**（1）构建、安装、冷启动**

```bash
$FLUTTER build apk --debug
$ADB install -r echo/build/app/outputs/flutter-apk/app-debug.apk
$ADB shell am force-stop com.everse.echo
$ADB shell am start -n com.everse.echo/.MainActivity
sleep 4.2   # 冷启动到可交互约 4~4.5s，过早注入手势会丢
```

**（2）截图**

单张截图必须用 `exec-out`——它按二进制透传，旧式
`adb shell screencap -p > x.png` 会被 CRLF 转换损坏 PNG：

```bash
$ADB exec-out screencap -p > /tmp/shot.png
```

截「手势进行中」的画面：后台发起一个长时长 swipe，按时间差在期望相位截图：

```bash
($ADB shell input swipe 800 2050 800 1300 4500 &)
sleep 3.4
$ADB exec-out screencap -p > /tmp/arc_open.png
```

截图通常只需局部、且要缩小便于快速查看，用 ffmpeg 裁剪 + 缩放：

```bash
ffmpeg -y -i /tmp/shot.png \
  -vf "crop=1080:900:0:1100,scale=432:360" /tmp/shot_small.png
```

**（3）录屏**

```bash
$ADB shell screenrecord --bit-rate 8000000 /sdcard/rec.mp4  # Ctrl-C 停止
$ADB pull /sdcard/rec.mp4 /tmp/rec.mp4
```

注意：screenrecord 本身增加 GPU/IO 负载，录屏期间测到的帧率是最差工况；
做性能判定优先用 1.12 的 gfxinfo（且 Flutter 自渲染管线在 debug 包下
gfxinfo 只记到约 1 帧，精测帧率需 profile 包）。

**（4）抽帧与多帧合成（接触印样）**

按帧率或固定抽帧：

```bash
ffmpeg -i /tmp/rec.mp4 -vf fps=12 /tmp/frame_%03d.png      # 等间隔抽帧
ffmpeg -ss 1.2 -i /tmp/rec.mp4 -frames:v 1 /tmp/at_1_2.png # 单时刻取帧
```

多张帧合成一张总览图（tile 前先缩小，省时省空间）：

```bash
ffmpeg -i /tmp/frame_%03d.png \
  -vf "scale=270:-1,tile=4x3" /tmp/contact_sheet.png
```

**坑**：tile 滤镜偶发整页全黑或错乱——这是滤镜问题，不要据全黑图
下结论，逐张打开原帧核对。

**（5）手势注入与判定纪律**

```bash
$ADB shell input swipe <x1> <y1> <x2> <y2> <duration_ms>
```

- `input swipe` 在该 MIUI 上不稳定：慢速长甩偶尔成功，多次会被系统抖成
  细碎移动、快捷弧根本不弹出（"那次成功是侥幸"即此）；快速短甩
  （约 300~350ms，终点落在目标按钮上）触发稳定。
- 因此：注入手势失败不等于功能坏了——一轮里安排多次尝试 / 改用时长，
  仍无法确认时交给用户手指验证；截图证据优先于"应该触发了"的推测。
- 注入坐标是**物理像素**；从 Flutter 逻辑坐标换算 ×2.75，
  截图反推 dp 则 ÷2.75。

**（6）临时探针 / 可视化件**

- 需要验证几何（如曲线形状）时，优先临时 `CustomPaint` 直接画在界面上、
  真机看实物，验收后立即删除，不留在交付里。
- 临时 Dart 探针不能放 `/tmp`——无法解析 `package:` 导入；
  放在项目内（如 `echo/test/tmp_probe/`）以 `flutter test` 运行，跑完即删。

## 2. 交付门禁（工具可换，门禁不变）【铁律】

无论以后是否引入 CI，每次交付前都必须满足（门禁项增减走 RCR）：

1. **静态分析零问题**（当前：`cd echo && flutter analyze`）。
2. **全部测试通过**（当前：`flutter test`）。
3. **手感相关改动完成真机回归**，基础手势全部过一遍：横滑、点圆点翻页、
   上甩及反悔、双击直达、长按搜索、多指边界（真机取证命令见 1.15）。
4. **新行为补测试；修 bug 优先补能复现该 bug 的回归测试。**
5. **文档对照审计**：architecture.md / glossary.md 与改动逐句核对。

### 测试写法约定

- 时间相关逻辑遵循 1.9：物理 / 倒计时走帧时钟，用 `tester.pump(...)` 手动推进，
  **不能用 pumpAndSettle**（存在持续运行的 ticker 时会永不结束）。
- 测试坐标若依赖具体几何，从几何常量计算，不要散落魔数；几何调整时同步更新测试。
- 优先给纯逻辑（物理、状态服务、几何 / 手势判定）写不依赖 widget 树的单元测试，
  不要全部堆进 pump 整个 App 的集成用例。
- UI 文案在多处复用时，用精确 Finder（`findsNWidgets`、作用域 descendant）
  避免 `find.text` 歧义；交互形态变更（如 Dialog → Route）时先补路由注册再改断言。

## 3. 历史事故档案

记录"症状 → 根因 → 对应原则"。具体手段可能过时，但更换手段前必须确认
同类问题不会复发。

| # | 症状 | 根因 | 对应原则 |
|---|---|---|---|
| 1 | 搜索框开合动画静默失效 | Stack 中部条件插入无 key 节点，框架错位配对，渲染对象销毁重建，AnimatedSize 首帧即终态 | [1.6](#16-元素身份必须稳定) |
| 2 | 历史胶囊自适应长度消失 | Container 设 alignment 后在有限宽度下撑满可用宽度 | 1.10 |

| 4 | 冷启动异常 / GlobalKey 重挂载断言 | 首帧高负载期运行时测量触发布局重挂载 | [1.8](#18-几何的事实来源唯一且视觉与命中一致) |
| 5 | fuse 倒计时瞬间烧完 | 帧外读取过期帧时间戳（首帧前为 0）作为烧蚀基准 | [1.9](#19-时间相关行为要可确定地测试) |

| 7 | 锚点呼吸/急闪光效冻结 | DecoratedBox 只在首帧取一次动画值，无逐帧订阅 | 1.10 |
| 8 | 停留/倒计时逻辑无法确定性测试 | 墙钟 Stopwatch 不随测试 pump 推进 | 1.9 |
| 9 | 快速扫过/双击跳转途经页面被误判已读 | 已读应基于"同页连续停留达阈值"，而非"经过即读" | 见下 |
| 10 | 搜索面板展开后自动关闭 | 失焦与重建链路问题（元素身份 + 焦点延时判断） | 1.6 / 1.9 |
| 11 | 搜索胶囊边框偏细；开合动画中端部出现椭圆角/矩形遮罩感 | 描边跨盒缘被 ClipRRect 裁掉外侧半条；999 名义圆角被渲染器横纵独立夹取 | 1.10 |

**事故 9 的产品规则**：在同一页连续停留 ≥700ms 才算查看；快速扫过、
按住圆点连翻、双击直达途经的中转页不算已读。实现上以独立监听器观察激活页变化、
每次变化重置计时（不复用会被静音的翻页回调）。手势 / 翻页机制变化时此判定需重新验证。
